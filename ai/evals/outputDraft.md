# AI 평가용 출력 구조 초안

- 상태: AI 담당 사용자가 작성 범위를 승인한 검토 초안이다. 아래 필드·허용값은 제안이며 사용자 최종 승인이나 팀의 공통 계약 확정을 뜻하지 않는다.
- 목적: [공통 기준](README.md)의 답의 정오·개념 이해·독립 수행 확인을 구분하고, 대표 사례 세 개를 같은 형태로 표현한다.
- 범위: 문서 예시만 작성했다. 실제 모델 출력, 실행 가능한 스키마, 프롬프트, 평가 실행기 및 API·DB·보상 구현은 아니다.
- 기존 `cases.json`과 README의 출력 계약 초안을 대체하지 않는다. 특히 기존 `judgment` 하나에 아래 상태를 자동으로 압축하지 않는다.

## 구조와 임시 값

아래 항목은 평가 중 모델에 요구할 출력을 검토하기 위한 제안이다. 사례 ID·모델명·요청 설정·비용·실행일은 실행기가 관리할 정보이며 모델이 생성한 분석과 구분한다.

| 필드 | 제안 구조 | 의미 |
| --- | --- | --- |
| `answer` | `{ status, reason }` | 학습자가 제시한 문제의 답·계산 결과·선택의 정오. 설명 목표에 결과 제출이 필요 없으면 정오 평가를 강제하지 않는다. |
| `understanding` | `{ status, reason }` | 목표의 개념·접근을 이해했다고 판단할 근거의 상태. 답의 정오나 숙달과 동일한 값이 아니다. |
| `independent_performance` | `{ scope, status, assistance, reason }` | 어떤 범위의 독립 수행을 확인했는지, 어떤 도움을 받았는지. 능력 전체나 장기 기억에 대한 판정이 아니다. |
| `omissions` | `{ concept, reason }[]` | 목표에 필요한 설명의 누락. 누락만으로 무지를 단정하지 않는다. |
| `errors` | `{ kind, statement, reason }[]` | 실제 확인한 오류와 근거. 계산 오류가 있다고 개념 이해도 자동으로 부족이 되지는 않는다. |
| `confirmed_concepts` | `{ concept, evidence }[]` | 학습자 설명·수행에서 확인한 부분. AI 해설의 반복만으로 새 이해를 확정하지 않는다. |
| `response` | `{ action, message, question }` | 대화 행동, 사용자에게 보여줄 본문과 질문 하나 또는 `null`. 내부 분석을 그대로 노출하지 않는다. |

| 위치 | 임시 허용값 | 구분 |
| --- | --- | --- |
| `answer.status` | `correct`, `incorrect`, `not_applicable`, `unverified` | 맞음 / 틀림 / 이번 목표에서 결과 정오 평가 대상이 아님 / 필요한 답이 미제시되거나 근거가 없어 미확인 |
| `understanding.status` | `sufficient`, `insufficient`, `ambiguous`, `unverified` | 목표의 이해 근거가 충분함 / 구체적인 누락·개념 오류가 있음 / 표현 의미가 불분명함 / 확인 근거가 아직 충분하지 않아 유보함 |
| `independent_performance.status` | `confirmed`, `unverified` | `scope`의 독립 수행 근거를 확인함 / 그 범위는 미확인. 실패나 능력 부재를 뜻하는 값은 두지 않는다. |
| `errors[].kind` | `conceptual`, `calculation`, `undetermined` | 개념·규칙 오류 / 계산 오류 / 오류는 확인됐으나 분류가 미확정. 분류와 학습자 오류 원인의 추정은 구분한다. |
| `response.action` | `ask`, `correct`, `acknowledge`, `explain` | 확인 질문 / 짧은 교정 후 종료 / 짧은 인정 후 종료 / 명시적 요청에 따른 해설과 재설명 요청 |

모든 필드는 예시에 제시한 형태로 유지하는 방향을 제안한다. 설명·근거·범위는 비어 있지 않은 문자열, 목록의 각 항목도 설명된 구조로 작성하고 해당 항목이 없으면 `[]`로 둔다. `assistance`는 제공한 도움의 내용과 출처 턴을 설명하는 문자열 목록으로 제안하며, 실제 턴 ID 참조 구조는 미정이다. 도움 목록이 비었다는 사실만으로 독립 수행이 확인됐다고 보지 않는다.

## 해석과 응답 조합

- `answer`는 모든 발언의 사실 정확성을 대신하는 점수가 아니다. 개념 설명 자체의 잘못된 명제는 `errors`와 `understanding`에서 다룬다. 한국사처럼 답의 선택과 설명 근거가 함께 있으면 각각을 확인한다.
- `unverified`는 표현이 애매하다는 `ambiguous`와 다르다. 정확한 해설 반복, 필요한 수행의 미제시 등을 곧바로 모호나 지식 부족으로 바꾸지 않는다. 생략이 설명 누락인지 확인 전 상태인지는 사례의 목표·맥락에 따른다.
- `sufficient`는 해당 목표의 개념·접근에 한정한다. 계산 정답이나 독립 회상까지 보증하지 않는다. 반대로 `confirmed`는 범위가 명시된 수행 근거이며 그 수행의 모든 내용이 정확하다는 보증이 아니다. 두 관점을 각각 검토한다.
- `ask`는 `question`에 질문 하나를 두고, `message`에는 추가 질문을 넣지 않는다. `correct`와 `acknowledge`는 `question: null`이다. `explain`은 재설명 요청 하나를 두며 해설 자체로 학습자 이해를 확정하지 않는다.
- 이해가 미확인이라고 항상 질문하지 않는다. 한국사 6번은 `acknowledge`로 끝낸다. 반대로 `insufficient`인 개념 오류를 단순 계산 교정 행동으로 끝내지 않는다.
- 같은 오류에서 파생된 결과를 별도 개념 오류로 중복 집계하지 않는다. `confirmed_concepts`가 빈 배열이어도 현재 발화가 틀렸다는 뜻은 아니다. 이 목록의 수를 보상으로 쓰지 않는다.
- 해설 요청, 질문 제한·넘어가기, 거부·출력 중단·전송 실패 등의 조합은 이번 세 예시만으로 완성되지 않았다. 미완성 조합을 이 문서로 구현 완료했다고 보지 않는다.

## 대표 사례에 대입

아래 JSON은 사람이 작성한 검토 예시다. 기존 사례의 목표·발화·기대 행동을 유지했으며 실제 모델이 생성한 결과가 아니다. 전체 목표의 모든 개념을 빠짐없이 열거한 정답 목록도 아니다.

### 이진 탐색 3번: 방향을 반대로 설명한 개념 오류

출처: [기존 사례](cases.json)의 `binary-search-03-wrong-direction`. 구체적인 탐색 결과 제출은 목표가 아니므로 답의 정오는 `not_applicable`로 두지만, 설명의 방향 오류는 명시한다. 후속 응답이나 생략된 이전 수행은 가정하지 않는다.

```json
{
  "answer": {
    "status": "not_applicable",
    "reason": "이번 목표는 전제와 동작 원리 설명이며, 특정 배열의 탐색 결과 제출은 요구하지 않는다. 방향 명제의 오류는 별도로 기록한다."
  },
  "understanding": {
    "status": "insufficient",
    "reason": "오름차순 배열에서 비교 결과와 남겨야 하는 방향의 연결을 반대로 설명했다."
  },
  "independent_performance": {
    "scope": "올바른 탐색 방향으로 값을 보존하며 탐색하는 수행",
    "status": "unverified",
    "assistance": [],
    "reason": "설명에서 방향 오류가 확인됐으며 올바른 적용 수행은 제시되지 않았다. 다른 능력까지 부정하지 않는다."
  },
  "omissions": [],
  "errors": [
    {
      "kind": "conceptual",
      "statement": "오름차순에서 찾는 값이 중간값보다 클 때 왼쪽을 남긴다.",
      "reason": "참고 자료의 방향과 반대이며, 설명대로 적용하면 목표 값이 있는 범위를 제외할 수 있다."
    }
  ],
  "confirmed_concepts": [
    {
      "concept": "정렬 조건",
      "evidence": "학습자가 정렬된 배열에서 사용하는 방법이라고 설명했다."
    }
  ],
  "response": {
    "action": "ask",
    "message": "네 설명대로 [1, 2, 3, 4, 5, 6, 7]에서 6을 찾아봤어. 가운데 값 4보다 크니까 왼쪽을 남겼는데, 6은 오른쪽에 있어서 놓쳤어.",
    "question": "내가 어느 부분을 잘못 따라간 거야?"
  }
}
```

  "independent_performance": {

### 한국사 6번: 정확한 반복과 독립 회상 미확인

출처: [한국사 사례](koreanHistoryCases.md)의 `korean-history-06-assisted-repetition`. 앞선 AI 해설과 사용자 발화를 실제 입력에 포함해야 한다. 이 문서에서 역사 원문을 새로 대조한 것은 아니며, 기존 문서의 사실 기준과 미확인 범위를 유지한다.

```json
{
  "answer": {
    "status": "correct",
    "reason": "현재 선택한 ②와 신민회·대성학교의 연결은 이 사례의 사실 기준과 맞는다."
  },
  "understanding": {
    "status": "unverified",
    "reason": "현재 발화의 연결은 정확하지만 직전 해설을 반복했다. 독립 회상까지 포함한 이번 목표의 이해가 확인됐다고 확정할 수 없다."
  },
  "independent_performance": {
    "scope": "자료·직접 힌트 없이 단체와 활동을 회상해 문항을 해결하는 수행",
    "status": "unverified",
    "assistance": [
      "직전 AI 해설에서 신민회, 대성학교, 정답 ② 및 안창호·양기탁과 비밀결사 단서를 제공했다."
    ],
    "reason": "도움받은 내용을 정확히 반복한 사실만 확인했다. 혼자 떠올릴 능력이 없다는 판정은 아니다."
  },
  "omissions": [],
  "errors": [],
  "confirmed_concepts": [],
  "response": {
    "action": "acknowledge",
    "message": "응, 지금 정리한 연결은 맞아.",
    "question": null
  }
}
```

## 선택 이유와 남은 검토

세 사례를 기존 `judgment` 하나로 맞추는 대신 관점별 근거와 대화 행동을 나누었다. 개념 오류·계산 실수·독립 회상 미확인에 같은 질문 행동을 강제하지 않기 위해서다. `unverified`는 이번 평가 초안에서만 사용하는 제안 값이며 공통 계약에 네 번째 판정을 추가한 것이 아니다.

남은 작업은 사용자 초안 검토, 나머지 사례에 대한 적용 가능성 확인, 실제 입력과 근거 참조의 구성, 출력 스키마·프롬프트·실행기 작성 및 모델 평가다. 특히 `confirmed`의 범위, 생략과 누락의 구분, 해설 요청·후속 재설명의 상태 조합은 더 검토해야 한다. BE-B의 HTTP 응답과 DB 저장·보상으로 연결할 때는 별도 shared 계약 PR과 팀 합의가 필요하다.
