# 텍스트 시연 시나리오: 이분 탐색

설명 입력 → 실제 AI 역질문 → 재설명 → 이해 확인이 앱에서 이어지는지 확인하고 촬영한다. 기존 단일 호출 평가와 별개의 다중 턴 연동 시나리오 초안이다.

- 작성일: 2026-11-04.
- 계약 기준: PR #17, main `bb151a0`. AI 분석 구현 #16도 main에 반영됐다.
- 아직 이 시나리오로 실제 모델 호출·앱 연동 검증·촬영을 수행하지 않았다. 아래 AI 질문 예시는 실행 결과가 아니다.
- 추가 유료 호출은 별도 승인 후 진행한다. 문서 작성은 API를 호출하지 않는다.
- 학습자 입력만 준비한다. 실제 AI 발화를 고정 문구로 대체하거나 원하는 종료 행동으로 바꾸지 않는다.

## 준비 조건

- 실제 API 모드와 익명 로그인, 서버에 존재하는 사용자 소유 폴더·활성 세션을 사용한다. mock ID로 실제 API를 요청하지 않는다.
- 폴더 동물은 러버덕을 시연 후보로 사용한다. 이 선택이 서비스의 기본 캐릭터 확정을 뜻하지는 않는다.
- 이번 시연에서는 참고 자료 없이 모델 일반 지식을 사용한다. 정확성 한계 안내는 서비스 진입부 등 합의한 UI에서 확인하고 매 AI 발화에 반복 삽입하지 않는다.
- BE의 API 주소·인증 방법·요청/응답 예시와 FE의 실제 API 연결 상태를 확인한다. 서버 API 키나 사용자 인증 토큰을 촬영 화면·로그·기록에 노출하지 않는다.
- 다음 분석에는 서버가 저장한 실제 사용자·AI 발화를 순서대로 복원한다. `message` 뒤에 `question`을 이어 사용하고, null 질문은 생략한다. 현재 입력은 `user_message`에만 넣는다. 내부 근거와 앱의 `question_text`로 실제 이력을 대신하지 않는다.

## 촬영 순서와 복사할 입력

### 1. 학습 목표

> 정렬된 배열에서 이분 탐색이 한쪽 범위를 제외할 수 있는 이유와 종료 조건을 설명한다.

시간 복잡도 증명이나 구현 세부사항은 이번 목표에 넣지 않는다.

### 2. 첫 설명

> 이분 탐색은 오름차순으로 정렬된 배열에서 가운데 값을 확인하는 방법이야. 찾는 값이 가운데 값보다 크면 오른쪽을, 작으면 왼쪽을 계속 찾아. 이렇게 범위를 줄여서 값을 찾는 거야.

방법은 설명하지만 정렬 덕분에 한쪽을 안전하게 제외하는 근거와 종료 조건은 생략했다. 오답을 일부러 넣는 시나리오가 아니다.

### 3. 실제 AI 역질문 확인

기대 방향은 빠진 연결에 대한 질문이다. 예를 들면 다음과 같다.

> 찾는 값이 가운데 값보다 클 때, 왼쪽에는 없다고 어떻게 확신할 수 있어?

문장 일치를 요구하지 않는다. 종료 조건 등 다른 목표 범위의 빈 부분을 물어도 실제 질문에 맞춰 답한다. 질문을 만들기 위해 충분·부족·모호·미확인 값을 강제 지정하지 않는다.

### 4. 재설명 준비안

> 오름차순으로 정렬되어 있으니까 가운데 왼쪽의 값들은 모두 가운데 값보다 작거나 같아. 따라서 찾는 값이 가운데 값보다 크면 왼쪽과 가운데는 후보에서 제외할 수 있어. 작은 경우에는 반대로 오른쪽과 가운데를 제외해. 남은 범위에서도 이 과정을 반복하고, 가운데 값과 같으면 찾은 거야. 같아지기 전에 탐색 범위가 비면 배열에 없는 값이라고 끝내.

실제 질문을 먼저 읽고 필요한 부분을 중심으로 답한다. 위 문장을 질문과 관계없이 자동 전송하지 않는다. 작은 예가 필요하면 정렬된 배열 `[2, 5, 8, 12, 16]`에서 12를 찾는 과정을 보충할 수 있다.

### 5. 이해 확인과 종료

- AI가 재설명과 앞선 대화를 반영했는지 확인한다.
- 학습 목표의 연결과 종료 조건이 충분히 설명되면 질문 없는 이해 확인을 기대한다. 행동은 실제 응답을 따른다.
- 정당한 추가 질문이면 계속 답한다. 한 번의 재설명이나 총 두 번의 질문 안에 끝내도록 강제하지 않는다.
- 실제 `message`·`question`을 그대로 표시한다. `ask`·`explain`은 답변 대기, `correct`·`acknowledge`는 해당 대화 마무리로 처리한다.
- 다음 주제 자동 제안은 이번 시연에서 제외한다. 미확인·넘어가기를 충분 판정으로 바꾸지 않는다. 대화 마무리만으로 독립 숙달·세션 종료·보상을 확정하지 않는다.

## 성공 기준과 실패 구분

| 확인 항목 | 통과 기준 |
| --- | --- |
| 실제 호출 | mock이 아니라 서버의 실제 분석 응답을 표시함 |
| 첫 질문 | 목표 범위의 빠진 연결을 묻는 실제 AI 질문이 보임 |
| 재설명 | 사용자가 질문을 읽고 답을 제출할 수 있음 |
| 이전 대화 | 요청 구성에서 실제 사용자·AI 이력이 보존되고, 응답도 그 흐름을 반영함 |
| 이해 확인 | 목표가 충족된 뒤 실제 이해 확인 발화를 표시하며 필요 없는 같은 질문을 반복하지 않음 |
| 실패 처리 | 호출·검증 실패를 가짜 성공이나 충분 판정으로 바꾸지 않음 |

화면에 대화가 이어져 보이는 것만으로 서버 이력 복원을 입증하지 않는다. BE 구현·비용 없는 시험과 함께 확인한다. 한 장면 성공을 22개 평가 전체 행동 통과나 반복 안정성으로 일반화하지 않는다.

AI가 첫 설명을 그대로 인정하거나, 타당한 질문을 하지 않거나, 충분히 답한 내용을 계속 재질문하면 관찰 결과로 남긴다. 결과를 미리 정한 대사로 교체하지 않는다. API·인증·저장·화면 전환 실패와 AI 행동 문제를 구분한다.

## 실행 기록 양식

- 실행일 / 앱·서버·AI 커밋 / 모델 / 동물:
- 실제 API 연결·인증·활성 세션 확인 여부:
- 실제 첫 설명 / AI message·question / 재설명 / 이후 AI 발화:
- 응답의 세 상태와 action:
- 실제 호출 횟수 / 확인 가능한 사용량·비용:
- 성공 기준별 결과 / 실패 단계·오류 코드:
- 촬영 여부 / 영상 위치:

실제 발화는 해당 시연 기록에만 보관하고 비밀 키·인증 토큰은 기록하지 않는다. 서버 공통 로그에 요청·응답 본문을 추가하는 방식으로 확인하지 않는다.
