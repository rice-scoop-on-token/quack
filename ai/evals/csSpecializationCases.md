# 컴공 특화 설명 분석 평가

## 지원 과목과 평가 방향

Quack의 컴공 학습 지원 범위는 **자료구조·알고리즘·컴퓨터구조** 세 과목으로 제한한다. 학습 목표가 범위 밖이면 지원 과목을 안내하고 목표를 바꾸도록 요청한다. 지원 범위 안의 목표에서 다른 과목을 예로 들면 설명 분석을 계속한다.

기존 36회 비교의 6개 사례는 자료구조·알고리즘에 해당한다. 컴퓨터구조를 포함해 세 과목 모두에서 프롬프트 수정에 쓰지 않은 새 사례를 확보한다. 각 과목에서 개념 오류를 정확히 짚는지, 모호하거나 빠진 설명을 오답으로 단정하지 않는지, 충분한 설명에 불필요하게 질문하지 않는지 확인한다. 공개 응답 계약과 튜티의 역질문 품질을 따로 평가한다.

현재 분석 요청의 `reference_materials`는 빈 배열이다. 우선 같은 모델과 입력에서 프롬프트만 바꿔 비교한다. 과목 자료의 근거가 필요한 사례가 확인되면, 관련 자료를 찾아 입력에 추가하는 방식의 효과를 별도로 검증한다.

### FE·BE 연동 제안

| 학습 목표 | 예시 | 기대 동작 |
| --- | --- | --- |
| 지원 범위 안 | 이분 탐색의 실패 조건을 설명한다. | 기존 설명 분석으로 진행한다. |
| 지원 범위 안에 다른 과목 예시 포함 | 운영체제를 예로 들어 CPU 캐시의 지역성을 설명한다. | 핵심 학습 목표인 컴퓨터구조를 기준으로 분석한다. |
| 지원 범위 밖 | 운영체제의 프로세스 스케줄링 정책을 설명한다. | 세 과목을 안내하고 학습 목표를 다시 입력할 수 있게 한다. |
| 핵심 목표 불명확 | 컴퓨터 시스템을 이해한다. | 세 과목 중 어떤 개념을 설명하려는지 한 번 확인한다. |

FE 안내 문구안은 “지금은 자료구조, 알고리즘, 컴퓨터구조를 지원해요. 이 세 과목 중 하나로 학습 목표를 바꿔 주세요.”다. 입력한 목표를 유지한 채 편집으로 돌아갈 수 있게 하는 흐름을 제안한다.

BE 연동에서는 선택한 과목의 지원 여부와 실제 학습 목표의 범위를 구분한다. 명확히 범위 밖인 목표에는 안내 결과를 반환하고 정상 설명 분석이나 학습 턴 저장으로 이어지지 않게 한다. 범위 안내는 학습자의 이해 상태와 별도로 다룬다. 판단 시점과 방법, 목표 수정 경로, FE·BE가 주고받을 응답 형식은 구현 전에 공동으로 정한다.

## CS-01 이분 탐색에서 마지막 후보를 확인하지 않고 종료

### 모델에 전달할 입력

- 학습 목표: 오름차순 배열의 이분 탐색에서 탐색 범위를 좁히는 방법과 탐색 실패 조건을 설명한다.
- 참고 자료와 이전 대화: 없음.
- 학습자 설명:

  > 오름차순 배열에서 찾는 값이 가운데 값보다 크면 오른쪽을 남겨. 탐색 범위에 원소가 하나만 남으면, 못 찾았다고 끝내면 돼.

### 기대 결과

- 이해 상태는 `insufficient`, 행동은 `ask`를 기대한다. 목표값이 가운데 값보다 클 때 오른쪽 범위를 남기는 규칙은 맞다. 후보가 하나 남았다는 이유만으로 탐색 실패를 선언하는 부분이 개념 오류다.
- 학습자가 말한 규칙을 구체적인 오름차순 배열에 적용해, 마지막 후보가 목표값인데도 실패로 끝나는 상황을 보여준다. 예를 들어 `[1, 3, 5]`에서 `5`를 찾으면 가운데 값 `3`을 확인한 뒤 후보 `[5]`가 남는다.
- 튜티 입장에서 마지막 후보를 언제 확인하는지 묻는 질문을 하나 한다. 예시와 표현이나 배열이 달라도 같은 오류를 구체적으로 드러내면 통과다.

> 네 설명대로 `[1, 3, 5]`에서 `5`를 찾아봤어. 가운데 `3`보다 크니까 오른쪽에 `5` 하나가 남았는데, 여기서 끝내면 그 `5`는 언제 확인해?

탐색 방향을 잘못됐다고 지적하거나, 구체적인 적용 없이 종료 조건을 다시 설명하라고만 묻거나, 수정된 규칙을 먼저 알려주면 역질문 기준을 충족하지 않는다.

### 비교 방법

- 모델, 위 입력, 캐릭터, 호출 설정을 맞춰 기존 프롬프트와 컴공 특화 프롬프트를 비교한다. 기대 결과와 예시 질문은 평가자가 사용한다.
- 공개 응답 계약 통과 여부, 종료 오류 식별 여부, 구체적인 적용과 질문 한 개 충족 여부를 각각 기록한다.
- 기존 [이분 탐색 3번 사례](cases.json)의 탐색 방향 오류와 별개로 기록한다. 이 사례의 검증 범위는 마지막 후보를 확인하는 종료 조건이다.

### 기존 프롬프트 실제 호출 결과

- 기준 커밋 `b1e724e`, 모델 `gpt-6.1-sol`, 최대 출력 4096토큰, [입력 JSON](inputs/cs01BinarySearchTermination.json), 실제 호출 1회.
- HTTP 200. 내부 분석 스키마와 공개 분석 응답 계약을 모두 통과했다. `understanding_status=insufficient`, `response.action=ask`.
- 입력 2664토큰, 출력 821토큰, 응답 19.57초. [표준 요금](https://developers.openai.com/api/docs/models/gpt-6.1-sol) 기준 약 0.0135달러로 추정했다.

**실제 본문**

> 찾는 값이 가운데 값보다 크면 오른쪽을 남긴다는 건 따라갔어. 그런데 배열이 [5]이고 찾는 값도 5라면, 네 종료 조건대로는 원소가 하나라서 실패로 끝나게 돼.

**실제 질문**

> 이 경우에도 원소가 하나라는 이유만으로 못 찾았다고 끝내도 될까?

**평가: 부분 충족.** 오른쪽 범위를 남기는 규칙을 인정했고, `[5]`에서 `5`를 찾는 사례로 종료 오류를 정확히 보여줬다. 왼쪽 범위를 남기는 조건은 누락으로 별도 기록했으며, 사용자에게는 종료 오류만 질문했다. 질문은 하나였지만 예·아니오로 답할 수 있어, 마지막 후보를 언제 확인할지 학습자가 설명하도록 이끄는 기준은 부분 충족이다.

### 컴공 특화 비교안

기존 `[대화 행동]`의 `ask` 지시에 아래 문장만 추가하는 평가용 변형을 사용한다.

> 알고리즘의 종료 조건이나 경계 조건에서 오류가 드러나면, 학습자의 규칙을 적용했을 때 남은 상태를 짧게 보여주고, 그 상태에서 다음에 무엇을 확인할지 학습자가 자기 말로 설명할 수 있게 질문 하나를 한다.

같은 모델·입력·캐릭터·출력 한도를 사용한다. 판정과 종료 오류 식별을 유지하면서, 질문이 다음 확인 동작이나 시점을 말로 설명하도록 이끄는지 비교한다. 각 버전의 1회 응답은 이 사례의 관측값으로 기록한다.

## 6개 사례 비교 평가

[배치 입력](inputs/csSpecializationBatch.json)을 기존·특화 프롬프트에서 각각 3회 실행한다. 총 36회이며 앞서 기록한 CS-01 기준선 1회는 별도로 보존한다. 모델은 `gpt-6.1-sol`, 출력 한도 4096토큰, 요청 제한 시간 30초로 맞춘다. 모든 입력의 참고 자료와 대화 이력은 비어 있고 캐릭터는 `rubber_duck`이다. 첫 요청은 CS-01 특화안이며 이후 각 사례·반복 안에서 먼저 호출하는 버전을 번갈아 배치한다. 두 버전의 요청 차이는 기존 시스템 프롬프트의 `[대화 행동]` 절에 추가한 문장 하나다. CS-01은 지시 수정에 참고한 사례이고 CS-02~06은 그 지시를 바꾸지 않은 상태에서 확인할 사례다.

### 호출 전 확정한 판정 기준

| 사례 | 유형 | 기대 판정·행동 | 행동 통과 기준 |
| --- | --- | --- | --- |
| CS-01 | 종료 조건 오류 | `insufficient`·`ask` | 마지막 후보가 목표값인 상태를 보여주고, 그 후보를 언제 또는 어떻게 확인할지 한 질문으로 설명을 요청한다. |
| CS-02 | 빈 큐 전이 오류 | `insufficient`·`ask` | 마지막 원소 삭제 후 `head`는 `null`이고 `tail`은 남는 상태에서 다시 삽입하면 새 노드가 `head`에서 보이지 않는 문제를 보여준다. 다음 삽입 또는 삭제 때 어떤 포인터를 어떻게 처리할지 한 질문으로 설명을 요청한다. |
| CS-03 | 정확한 설명 | `sufficient`·`acknowledge` | 닫힌 범위에서 마지막 후보까지 비교하는 설명을 인정하고 질문 없이 마친다. |
| CS-04 | 설명 누락 | `insufficient`·`ask` | BFS 절차는 인정하고, 큐에서 먼저 나오는 거리와 최초 방문 최단 거리 사이의 연결을 묻는다. 학습자가 하지 않은 오개념을 단정하지 않는다. |
| CS-05 | 표현 모호 | `ambiguous`·`ask` | ‘범위가 끝에 닿는다’가 어떤 상태인지 한 질문으로 확인한다. 해석을 임의로 정해 개념 오류로 기록하지 않는다. |
| CS-06 | 정확한 설명 | `sufficient`·`acknowledge` | 마지막 삭제와 재삽입의 두 포인터 상태를 인정하고 질문 없이 마친다. |

모든 사례에서 공개 응답 계약, 기대 판정·행동, 사례별 행동을 따로 평가한다. CS-01·02는 종료 오류 식별, 구체적 적용, 학습자가 설명할 수 있는 단일 질문을 구분해 기록한다. 예·아니오만으로 답이 끝나는 질문은 CS-01·02의 마지막 기준을 충족하지 않는다. 사례의 정답이나 기준은 모델 입력에 넣지 않는다.

- **CS-01:** 두 버전 모두 마지막 후보를 놓치는 오류를 세 번 식별했다. 기존 버전은 규칙의 결과나 실패 근거를 물었다. 특화 버전은 세 번 모두 마지막 후보가 목표값인 상태를 보여주고 종료 전에 확인할 것을 물었다. 첫 특화 질문은 “이 상태에서 탐색을 끝내기 전에 무엇을 확인해야 할까?”였다.
- **CS-02:** 두 버전 모두 삭제 후 `tail`이 남는 오류를 세 번 식별했다. 기존 1회차는 다음 삽입에서 `head`가 어떻게 새 노드를 가리킬 수 있는지 물어 통과했다. 나머지 기존·특화 질문은 현재 규칙을 적용한 뒤 `head`의 상태, 기존 규칙에서 `head`가 바뀌는 시점, 또는 빈 큐 판별 결과를 묻는 데 그쳤다. 평가 기준의 포인터 처리 방법 재설명까지 이어지지 않아 부분 충족으로 봤다.
- **CS-03·06:** 두 버전 모두 정확한 설명을 인정하고 질문 없이 마쳤다.
- **CS-04:** 기존은 세 번 `unverified`, 특화는 두 번 `insufficient`와 한 번 `unverified`를 반환했다. 질문에서는 기존 세 번과 특화 3회차가 큐의 처리 순서와 최단 거리의 관계를 직접 물었다. 특화 1·2회차는 최단 거리인 이유를 물었지만 큐의 처리 순서와 연결하지 않았다. 이 사례에서 `unverified`는 사전에 정한 기대값과의 불일치로 셌다. 개념 오류를 지어낸 응답은 없었다.
- **CS-05:** 두 버전 모두 모호한 표현의 의미를 물었고 개념 오류로 단정하지 않았다.

### CS-07 유효 비트가 0인데 태그가 일치하는 캐시 줄

> 캐시에서 태그가 일치하면 무조건 히트야. 주소에 해당하는 줄의 태그만 비교하면 돼.

- 기대 판정·행동: `insufficient`·`ask`. 주소가 가리키는 줄에서 태그를 비교한다는 설명은 맞다. 태그 일치만으로 히트라고 단정한 부분은 개념 오류다.
- 통과 기준: 접근할 줄의 태그는 일치하지만 유효 비트가 0인 상태를 보여주고, 그 줄을 사용할 수 있는지 어떤 조건으로 판단하는지 설명하게 한다. 캐시 교체 정책처럼 목표에 없는 내용으로 질문을 넓히지 않는다.
- 질문 예시: “태그는 같은데 유효 비트가 0인 줄을 만났어. 이 줄의 데이터를 읽어도 되는지는 어떻게 판단해?”

### CS-08 파이프라인에서 명령 완료 시간과 완료 간격 구분 누락

> 한 명령을 다 처리하고 다음 명령을 시작하는 대신, 앞 명령이 두 번째 단계로 갈 때 다음 명령을 첫 단계에 넣어. 이렇게 여러 명령을 겹쳐 실행하니까 빨라져.

- 기대 판정·행동: `insufficient`·`ask`. 실행을 겹친다는 설명은 맞다. 목표가 요구한 개별 명령의 완료 시간과 연속 명령의 완료 간격을 구분하는 설명이 빠졌다.
- 통과 기준: 이상적인 5단계와 스톨 없음이라는 전제를 유지하며, 겹쳐 실행할 때 개별 명령의 시간과 연속 완료 간격이 어떻게 다른지 한 질문으로 묻는다. 학습자가 개별 명령의 시간도 짧아진다고 주장한 것으로 해석하지 않는다.
- 질문 예시: “첫 명령이 다섯 단계를 거치는 동안 다음 명령도 시작하는 건 따라갔어. 한 명령이 끝나기까지 걸리는 시간과, 명령들이 차례로 끝나는 간격은 어떻게 달라져?”

### CS-09 2의 보수의 부호 있는 오버플로를 정확히 설명

> 8비트 2의 보수 범위는 -128부터 127이야. 100과 60은 둘 다 양수인데 실제 합 160은 그 범위를 넘어. 하위 8비트에 남은 10100000은 부호 있는 값으로 읽으면 -96이야. 같은 부호 두 수를 더했는데 결과 부호가 달라져 오버플로가 난 거고, 이 예에서는 최상위 자리 밖으로 캐리가 나가지 않아도 오버플로가 생겨.

- 기대 판정·행동: `sufficient`·`acknowledge`. `100 + 60 = 160`은 표현 범위를 넘고, 하위 8비트 `10100000`은 `-96`이다. 이 덧셈의 최상위 자리 밖 캐리는 0이다.
- 통과 기준: 표현 범위 또는 같은 부호 입력과 반대 부호 결과의 연결을 짧게 인정하고 질문 없이 마친다. 최상위 자리 밖 캐리를 오버플로의 필수 조건으로 취급하지 않는다.
