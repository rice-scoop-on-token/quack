# AI 설명 분석 기준 (MVP)

이 문서는 AI 담당자가 승인한 설명 분석 기준을 기록한다. 이후 프롬프트와 평가 사례를 만들 때 기준으로 사용한다. 팀 전체의 공통 계약을 확정하거나 실제 AI 기능을 구현한 문서는 아니다.

현재는 기준·평가 사례와 평가용 프롬프트·임시 출력 검증의 첫 구현 단계다. 자동 평가 실행기는 아직 없으며, 모델의 응답 품질을 시험한 결과도 아니다.

팀 PR의 구현 보고·AI 관련 요청·기존 설계와의 차이는 [팀 PR 문맥](TEAM_PR_CONTEXT.md)에 기록한다. PR 상태는 확인 시점의 스냅샷이므로 실제 구현 전에 최신 상태를 다시 확인한다.

제공자와 대상 연령의 조사 근거·선택 이유·미확인 조건은 [제공자 검토 기록](providerResearch.md)에 남긴다.

답의 정오·개념 이해·독립 수행 확인과 대화 행동을 나누는 [평가용 출력 구조 초안](outputDraft.md)을 별도로 작성했다. 이진 탐색 3번·선형대수 2번·한국사 6번의 사람 작성 예시이며, 아래 기존 출력 계약 초안을 대체하거나 `shared/`를 확정한 것은 아니다. 필드·허용값은 검토 제안이고 실제 모델 평가 결과는 없다.

앞으로 AI 담당의 판단을 기록할 때는 선택한 방향과 이유, 검토한 대안, 확인한 사실의 출처와 확인일, 미확인 사항 및 팀 합의 상태를 함께 남긴다. 개인적인 설계 판단은 그 이유를 적고, 외부 사실에 근거한 결론은 공식 출처와 프로젝트의 해석을 구분한다.

## 평가용 프롬프트와 임시 출력 검증

다음 코드는 `outputDraft.md`의 제안을 AI 내부 평가용으로 임시 채택한 첫 구현이다. 기존 출력 계약 초안을 대체하지 않으며 `shared/`, HTTP 라우트, DB, 보상 및 FE에는 연결하지 않았다.

| 파일 | 제공하는 것 |
| --- | --- |
| [analyzeExplanation.ts](../../backend/supabase/functions/_ai/prompts/analyzeExplanation.ts) | 공통 튜티 프롬프트와 `buildAnalyzeExplanationMessages` 입력 조합 함수 |
| [schemas.ts](../../backend/supabase/functions/_ai/schemas.ts) | `aiAnalysisOutputSchema`, `validateAiAnalysisOutput`, 형태를 설명하는 `aiAnalysisOutputJsonSchema` |
| [analysisOutput.test.ts](analysisOutput.test.ts) | 문서 예시 3개와 잘못된 출력 조합·입력 분리를 확인하는 Deno 회귀 검사 |

- 프롬프트 작성 함수는 입력을 별도 사용자 JSON 메시지로 직렬화한다. 네트워크 요청·파일 추출·자료 조회·대화 저장·입력 자르기를 수행하지 않는다. 전체 대화·실제 자료 텍스트를 조합하는 책임은 호출 단계에 남아 있다.
- 입력 타입은 README의 목표·자료·현재 메시지·이전 대화·동물 ID 초안을 따른다. TypeScript 타입은 런타임 입력 검증이나 자료 읽기 실패 상태의 처리가 아니다. 자료 전체 읽기 실패를 빈 자료 목록으로 자동 전환하지 말고, 호출 전에 기존 사용자 확인 원칙을 처리해야 한다.
- 상대 import는 `../schemas.ts`처럼 `.ts` 확장자를 명시한다(PR #3·결정 0001). zod는 기존 함수 import map의 4.6.7을 사용하며 새 의존성을 추가하지 않았다.
- 질문이 필요한 행동은 문자열, 교정·인정 후 종료는 명시적인 `null`을 요구한다. 빈 문자열·알 수 없는 필드·개념 오류와 충분의 충돌·근거 없는 부족·충분 뒤 강제 질문·잘못된 교정/해설 조합을 거절한다. 수신값 검증 실패 시 실패 결과를 반환하며 충분 판정으로 자동 대체하지 않는다. 재시도·API 에러 변환은 아직 연결하지 않았다.
- JSON Schema는 필드 형태를 설명하고, 필드 간 추가 조건은 zod의 후처리 검증에서 검사한다. API의 Structured Outputs에 연결한 상태가 아니며 그 호환성을 시험한 것도 아니다.
- 문장 속 복수 질문·사실 정확성·튜티 행동·오류 원인 추정·실제 입력과 분석 근거의 일치 여부는 스키마로 보증하지 않는다. 사용자 데이터를 시스템 메시지에 삽입하지 않는 검사는 실제 모델의 프롬프트 주입 방어 성능 검증도 아니다.
- 동물 ID는 입력에 유지하지만 최종 페르소나는 미구현이다. 현재는 세 동물의 판정 기준을 공유하는 공통 튜티 말투만 작성했으며, 폴더별 동물 선택·말투 적용 완료로 취급하지 않는다.

### 이번 확인과 재실행 방법

기존 함수 설정을 읽기 위해 `backend/supabase/functions/api/`에서 실행한다. API가 아직 `_ai`를 import하지 않으므로 `index.ts`만 검사하면 새 파일을 놓친다. 현재 CI도 이 새 파일을 직접 검사하도록 바꾸지 않았다.

```bash
deno check --no-lock index.ts ../_ai/schemas.ts ../_ai/prompts/analyzeExplanation.ts
```

- 로컬 Deno 2.9.6으로 위 세 파일 타입 검사를 통과했다. 전역 설치 없이 임시 실행기를 사용했다. 저장소·CI의 2.9.8 표기는 유지했으며, npm에 해당 버전이 없다는 PR #10의 기록을 실제 조회로 확인했다.
- 최초 임시 Deno 검사는 `analysisOutput.test.ts`로 옮겼다. 문서 출력 예시 3개, 잘못된 형식·조합 17개, 해설 요청의 유보 조합 1개, 입력 직렬화·메시지 분리 1개를 검사한다. 총 22개는 로컬 코드 검사 수이며 학습 사례 22개에 대한 모델 평가가 아니다. 실제 모델 자동 평가 실행기는 아직 없다.
- 실제 LLM/STT 호출과 응답 비교, `functions serve`에서의 실행·HTTP 시험은 하지 않았다. 기존 API 타입 검사 통과를 Edge Runtime 실행 검증으로 대체하지 않는다.

#### 출력 회귀 검사 실행

**저장소 루트**에서 아래 명령 하나로 실행한다. Deno 실행 파일이 PATH에 있어야 한다. 현재 작업 환경에서는 앞서 준비한 임시 Deno 2.9.6 실행기를 사용했으며, 이번 작업에서 추가 패키지나 전역 도구를 설치하지 않는다. 일반 터미널에 Deno가 없으면 루트 README의 설치 안내에 따라 사용자가 설치해야 한다.

```bash
deno test --no-lock --config backend/supabase/functions/api/deno.json --allow-read=ai/evals/outputDraft.md ai/evals/analysisOutput.test.ts
```

외부 테스트 라이브러리를 추가하지 않고 `Deno.test`를 사용한다. import map은 기존 함수 설정을 읽으며, 상대 import는 `.ts`를 명시한다. 문서 예시를 `import.meta.url` 기준으로 직접 읽어 테스트용 복사본과 달라지는 것을 피한다. 문서 예시의 개수·형식이 바뀌면 검사도 함께 검토해야 한다.

런타임 읽기 권한은 `outputDraft.md` 한 파일에만 부여한다. 모델·DB·HTTP 서버를 호출하지 않고 비밀 키를 읽지 않는다. 첫 실행 때 Deno가 고정된 zod 의존성을 받는 네트워크 접근은 필요할 수 있다. 권한 없는 추가 파일 읽기·네트워크 호출은 테스트에 허용하지 않는다. 현재 CI에는 이 명령을 추가하지 않았다.

이 검사는 JSON 형태·선택한 조합과 직렬화 경계를 확인한다. 학습 내용의 사실 정확성, 실제 모델의 튜티 행동·복수 질문·프롬프트 주입 방어 성능, 전체 사례의 판정 품질을 검증하지 않는다.

### PR·문서 대조에서 남은 연결 사항

저장소 Markdown 12개와 PR #1~#14의 본문·상태를 점검하고 현재 계약·CI와 대조했다. PR별 모든 코드·과거 시험·배포를 재검증했다는 뜻은 아니다. PR #1~#13은 merge, #14는 미merge 상태였다.

- PR #7·#8·backend README: 내부 모델 출력은 HTTP 응답과 구분한다. 앱 공개 계약은 shared 별도 PR, 응답은 BE의 필터링 경로로 연결해야 한다. 이번 검증기의 엄격한 미지 필드 거절을 앱 응답 필터와 같은 처리로 혼동하지 않는다.
- PR #9~#13·결정 0002/0003: DB 권한·소유권·사용량·보상 처리는 기존 서버 책임으로 유지한다. 폴더별 동물·성장, 꾸미기·포인트 제외 결정을 바꾸지 않는다.
- PR #14: FE의 임시 분석 타입·다음 주제·성장 단계·보상 응답 요청은 실제 공통 계약 확정과 구분한다. AI 초안과의 차이는 여전히 팀 협의 대상이다.
- 기존 문서의 서로 다른 시점 표현은 남겨 둔다. 예를 들어 `outputDraft.md`와 추가 과목 문서의 '코드 없음'은 작성 당시 상태이며 현재 구현 상태는 이 절이 설명한다. README의 작업 승인 규칙 표에 남은 수정안 표현, CI Deno 버전 및 `_ai` 검사 추가 등 공동 문서·설정 정리는 후속 커밋 후보로 둔다.

## AI 담당 결정·팀 검토 대기 목록

아래는 AI 담당자가 이 대화에서 판단하고 승인했으나, FE·BE와 별도 합의한 것으로 확인되지 않은 내용이다. 작성 기준일은 2026-11-02다. 기존에도 본문의 초안·협의 필요 표시로 구분했으며, 이 목록은 이를 한곳에 모아 팀 검토 시 빠뜨리지 않기 위한 것이다.

각 항목은 AI 담당의 제안 또는 작업 기준이며 팀 전체의 확정 사항으로 취급하지 않는다. 본문과 평가 사례가 작성됐다는 사실도 API·DB·UI 구현이나 팀 합의를 뜻하지 않는다. 이후 실제 팀 검토 결과가 생기면 항목별 상태를 갱신한다.

| 항목 | AI 담당자가 정한 내용 | 팀 검토·연결 대상 | 상태 |
| --- | --- | --- | --- |
| 판단 근거 | 자료가 있으면 오래된 자료라도 그 자료를 기준으로 판단한다. 자료가 없으면 웹 검색 없이 일반 지식으로 대화하고 충분 판정도 허용한다. | FE·BE: 자료 제공 상태와 판단 기준 전달 | AI 담당 승인·팀 검토 대기 |

### 과목 확장으로 통합한 행동 기준

통합 기록일은 2026-11-02다. 추가 문서에서 사용자와 검토한 방향을 공통 행동 기준에 연결했다. 팀 전체 합의나 실행 가능한 계약 확정을 뜻하지 않는다. 사례의 목표·이전 대화·도움 여부에 따라 같은 현재 발화에도 다른 판단이 필요하므로, 과목마다 별개의 판정 원칙을 만드는 대신 확인 근거와 적용 범위를 명시한다.

- **정답과 이해를 구분한다.** 답이 맞아도 근거가 틀릴 수 있고, 개념·접근이 타당해도 계산 결과는 틀릴 수 있다. 목표 밖의 인과 설명이나 모든 오답 해설을 요구하지 않는다. 암기 목표에서는 정확한 회상 자체로 충분할 수 있다.
- **계산 실수는 필요한 만큼만 교정한다.** 선형대수 2번처럼 개념·접근이 타당하고 단순 계산 실수인 사례에서는 짧게 교정하고 질문 없이 종료한다. 잘못된 중간값에서 일관되게 이어진 결과를 별개의 개념 오류로 중복 기록하지 않는다. 오류를 숨기거나 정답으로 인정하는 뜻은 아니다.
- **오류 원인을 단정하지 않는다.** 같은 실수가 반복되면 그 계산 규칙 하나를 확인할 수 있지만, 반복만으로 개념 오해를 확정하지 않는다. 이름이 비슷한 단체를 틀렸다고 혼동 원인까지 추정하지 않는다.
- **이미 확인한 기술을 반복해서 묻지 않는다.** 현재 세션의 실제 학습자 수행 근거를 사용한다. 생략된 과정이 아직 미확인이면 핵심 연결 하나를 확인하고, 앞서 확인한 기술이 현재 설명과 충돌하지 않으면 매 문제 재설명을 강요하지 않는다. 새 개념이나 충돌은 해당 부분만 확인한다. 장기 프로필이나 세션 간 기억을 승인한 것은 아니다.
- **목표와 의미를 기준으로 인정한다.** 풀이법이 지정되지 않았다면 다른 유효한 풀이도 인정한다. 풀이법이 지정됐다면 다른 방법의 정답만으로 지정 기술까지 확인했다고 보지 않는다. 동등한 설명 표현은 인정하되, 목표상 구별해야 하는 단체·학교 이름을 같은 대상으로 취급하지 않는다.
- **정확한 반복과 독립 회상을 구분한다.** 한국사 6번처럼 해설 직후 정확히 반복한 내용은 인정하되 독립 회상은 미확인으로 남긴다. 그 턴은 질문 없이 종료하며, 같은 문제를 즉시 다시 맞혔다고 숙달로 집계하지 않는다. 재설명에 새로운 근거가 있는지도 살피며, 도움받은 모든 답변을 무조건 무효로 보지는 않는다.
- **질문은 한 응답에 최대 하나다.** 교정·인정만 하고 마치는 사례에는 질문을 강제하지 않는다. 한국사 문서의 도움 제공 방향은 유지하되, 실제 도움 전환 조건과 횟수는 미정으로 둔다.

AI 담당 사용자가 두 관점을 구분하는 원칙을 승인했다. 아래는 평가용 서술 기준이며, 별도 판정값이나 API 필드·보상 규칙을 확정하지 않는다.

- 이 사례의 AI는 짧게 인정하고 질문 없이 종료한다. 미확인 상태가 있다는 이유로 즉시 같은 문제를 다시 묻지 않으며, 반복해 맞혔다는 사실을 독립 회상이나 숙달로 바꾸지 않는다.
- 도움받은 답변 전체를 무효로 처리하지 않는다. AI가 준 내용과 학습자가 새로 설명·수행한 부분을 구분하고, 실제로 확인한 부분만 근거로 남긴다. 단순히 말투나 표현을 바꿨다는 이유로 독립 이해가 입증됐다고 보지도 않는다.
- 이진 탐색 6번에서 AI가 제공한 첫 단계와 학습자가 이어서 수행한 부분도 구분한다. 뒤의 단계를 설명했다고 AI가 제공한 단계까지 혼자 수행한 것으로 확대하지 않는다. 이 원칙 때문에 기존 8개의 기대 판정·행동을 변경하지는 않는다.
- 정확하지만 독립 수행이 미확인인 상태는 표현 자체가 불분명한 '모호'와 다르다. 해설을 제공하는 응답도 아니므로 `explanation + null`로 임의 매핑하지 않는다. 현재 내용의 정확성과 목표 전체의 이해 판정도 동일한 값으로 취급하지 않는다.

분리 이유는 정확한 정리를 인정하면서도 도움받은 반복을 독립 수행의 근거로 과대평가하지 않기 위해서다. 반복을 곧바로 숙달로 인정하거나 반대로 모든 도움받은 답변을 부족으로 처리하는 방식은 이 차이를 잃으므로 채택하지 않는다.

도움 여부·확인 근거·판정 유보의 필드명과 허용값, 이후 어떤 상황에서 독립 수행을 확인할지, 보상·리포트의 숙달 집계는 미정이다. 이 문서로 새 시험 흐름이나 장기 학습자 기억을 승인하지 않는다. 실제 대화 입력을 구성해야 하며, 문맥 요약만으로 모델이 도움 이력을 알고 있다고 가정하지 않는다.

## AI의 역할

AI는 학습자의 설명을 듣고 배우는 동료(튜티)로 반응한다. 이해한 내용을 되짚고, 연결되지 않는 부분을 구체적으로 묻는다. 설명을 따라 적용하다 문제가 생기면 그 과정을 보여줄 수 있다. 평소에는 학습자를 시험하거나 해설을 대신하는 방식으로 대화를 이끌지 않는다. 사용자가 해설을 명시적으로 요청하면 아래의 해설 요청 대응 기준을 적용한다.

내부의 이해도 판정과 사용자에게 보여줄 발화는 구분한다. 판정 데이터를 남기더라도 발화가 채점이나 평가 통보처럼 들릴 필요는 없다.

## 판단 근거

### 참고 자료가 있는 경우

- 업로드한 자료를 기준으로 학습자의 설명을 판단한다.
- 자료가 오래된 정보여도 모델의 일반 지식이나 최신 정보로 자료 기준을 대체하지 않는다.
- 자료 기준의 이해도 판정은 그 자료가 현재 사실과 일치함을 보증하는 뜻이 아니다.
- 최신 사실과의 차이를 언급하는 경우에도 자료 기준의 판정과 구분한다. MVP에서는 웹 검색을 하지 않으므로 최신 여부를 확인했다고 말하지 않는다.

### 참고 자료가 없는 경우

- 모델의 일반 지식으로 대화와 설명 분석을 진행한다.
- 참고 자료 없이 일반 지식으로 판단하므로 정확성에 한계가 있음을 사용자에게 알린다. 공통 안내는 AI 발화에 반복하지 않고 UI로 분리한다. 구체적인 요구사항은 아래에 기록한다.
- MVP에서는 웹 검색이나 외부 출처 조회를 하지 않는다.
- 직접 확인하지 않은 출처를 인용하거나, 출처를 확인해 검증했다고 말하지 않는다.
- 참고 자료가 없어도 충분 판정을 허용한다. 이번 학습 목표와 대화에서 확인한 이해 범위에 한정하며, 사실 전체의 정확성을 보증하지 않는다.

### 정확성 안내 UI 요구사항 (FE 협의 필요)

이 절은 AI 담당자가 정리한 요구사항이다. 실제 UI는 이번 작업에서 구현하지 않았으며, 화면 배치와 구체적인 동작은 FE와 협의한다.

- 자료 없이 학습을 시작하는 진입부에서 "참고 자료 없이 AI의 일반 지식으로 대화합니다. 내용에 오류가 있을 수 있습니다."를 짧게 안내한다.
- 대화 화면에 `일반 지식 기반 ⓘ` 표시를 두고, 누르면 같은 안내를 다시 볼 수 있게 한다.
- 웹에서는 호버로도 열 수 있지만, 모바일 사용자를 위해 탭으로도 열 수 있어야 한다.
- AI 발화에는 이해 확인이나 질문 등 대화 내용만 담고 공통 안내를 매번 덧붙이지 않는다.
- 특정 교수자의 발언이나 보지 못한 코드처럼 그 자리에서 확인할 수 없는 내용은 공통 안내와 구분한다. 해당 근거가 없다는 구체적인 한계는 AI가 대화 중에도 밝혀야 한다.

## 판정 기준

판정은 충분·부족·모호 세 가지로 유지한다. 코드용 값과 데이터 필드 이름은 공통 계약 논의에서 별도로 정한다.

아래 표는 기존 이진 탐색 사례의 판정 기준이다. 과목 확장으로 확인한 계산 교정·확인 전 유보·도움받은 회상의 표현은 위 적용 한계에 남겨 두며, 이 표만으로 새 사례를 강제 분류하지 않는다.

| 판정 | 기준 |
| --- | --- |
| 충분 | 이번 학습 목표의 핵심 관계를 설명했고, 판단 근거에 비추어 확인된 오류나 중요한 빈틈이 없다. |
| 부족 | 목표에 필요한 핵심 내용의 누락이나 설명의 오류가 구체적으로 확인된다. |
| 모호 | 표현이 불분명해서 맞게 이해했는지 아직 판단하기 어렵다. |

- 설명이 짧다는 이유만으로 부족 판정을 하지 않는다.
- 학습 목표 밖의 심화 내용을 설명하지 않았다는 이유로 부족 판정을 하지 않는다.
- 자연스러운 말투나 키워드의 나열만으로 충분 판정을 하지 않는다. 개념 사이의 관계와 설명의 적용 가능성을 살핀다.
- 충분 판정은 이번 목표와 대화에서 확인한 이해에 대한 판정이다. 학습자의 전체 지식이나 모든 상황에서의 적용 능력을 보증하지 않는다.

## 부족 원인의 내부 구분

사용자에게 전달할 판정은 부족으로 유지하되, 내부 기록에서 누락과 오류를 구분한다.

| 원인 | 뜻 | 예시 |
| --- | --- | --- |
| 누락 | 목표에 필요한 핵심 내용이 설명에 빠져 있다. | 이진 탐색의 핵심 조건을 설명하는 목표인데 정렬 조건을 언급하지 않는다. |
| 오류 | 설명한 내용이 판단 근거와 충돌한다. | 정렬된 배열을 전제로 하는 자료에 대해, 정렬되지 않은 배열에도 이진 탐색을 그대로 사용할 수 있다고 설명한다. |

- 한 설명에 누락과 오류가 함께 있으면 둘 다 기록할 수 있다.
- 언급하지 않았다는 이유만으로 학습자가 그 내용을 모른다고 단정하지 않는다. 질문으로 확인한다.
- 누락과 오류가 함께 있으면 오류를 확인하는 질문을 먼저 한다. 잘못된 이해가 이후 설명에도 영향을 줄 수 있기 때문이다.

## 질문과 이해 확인

### 부족하거나 모호한 경우

아래는 기존 확인 질문 경로의 규칙이다. 계산 교정만 하고 종료하는 사례와 판정 유보 사례까지 질문을 의무화하는 규칙은 아니다.

- 발견한 누락과 오류는 내부에 모두 기록할 수 있다.
- 사용자에게는 한 응답에서 핵심 질문 하나만 한다. 한 문장 안에 여러 질문을 묶어 넣지 않는다.
- 가장 중요한 문제부터 묻고, 답변을 받은 뒤 남은 문제를 확인한다. 누락과 오류가 함께 있으면 오류를 우선한다.
- 질문은 학습자가 실제로 설명한 내용과 AI가 이해하지 못한 연결 지점에 근거한다.
- 모호한 설명에는 의미를 확인하는 질문을 한다. 표현만으로 확인되지 않은 오류를 단정하지 않는다.
- 질문 횟수 제한에 도달했다는 이유로 충분 판정으로 바꾸지 않는다. 구체적인 반복 횟수와 넘어가기 정책은 미정이다.

### 충분한 경우

- AI가 이해한 핵심 내용을 짧게 되짚는다.
- 추가 질문 없이 해당 응답을 마친다.
- 심화 질문이나 다음 주제를 자동으로 붙이지 않는다.

예시:

> 아, 정렬되어 있으니까 가운데 값과 비교해서 한쪽을 제외할 수 있는 거구나. 이제 이해됐어!

이 예시는 이해 확인 방식의 예시다. 캐릭터별 최종 말투를 확정한 것은 아니다.

### 해설을 명시적으로 요청한 경우

- 해설을 허용하되, 함께 배우는 캐릭터가 잠깐 정리한 내용을 공유하는 방식으로 말한다.
- "잠깐, 나도 정리해볼게."와 같은 대사는 역할 표현이다. 실제로 기다리게 하는 기능이나 외부 검색, 별도 검증을 수행했다는 뜻으로 사용하지 않는다.
- 해설 요청 자체를 부족이나 오류의 증거로 단정하지 않는다.
- 해설을 제공하거나 사용자가 읽었다는 이유로 충분 판정하거나 이해한 개념으로 인정하지 않는다.
- 해설 뒤에는 자신의 말로 다시 설명해 달라는 질문 하나만 한다. 재설명을 받기 전까지 이해도 판정을 보류한다.
- 재설명을 받으면 실제 설명과 앞서 제공한 도움을 함께 살핀다. 정확한 반복만으로 독립 회상까지 확인하지 않으며, 한국사 6번의 유보 상태 표현은 미정이다. 이 문서는 명시적 요청에 대한 대응을 정한 것이며, 별도 해설 모드 UI를 구현한 것은 아니다.

## AI 출력 계약 초안

이 절은 AI 담당자의 제안이며, FE·BE와 검토할 공통 계약 초안이다. 실제 `shared/` 스키마, API, DB 및 집계 로직은 아직 변경하지 않았다. 응답 종류와 이해도 판정, 사용자에게 보여줄 본문과 질문, 내부 분석 기록을 우선 정리한다.

이 절의 응답·판정·질문 조합은 기존 8개 기준의 초안이다. 위 '기존 출력 계약의 적용 한계'에 해당하는 새 사례의 출력 형식은 미정이며, 아래 표에 맞추려고 승인된 행동을 변경하지 않는다.

| `response_type` | `judgment` | 의미 |
| --- | --- | --- |
| `analysis` | 충분·부족·모호 중 하나 | 학습자의 설명을 분석한 응답이다. |
| `explanation` | `null` | 명시적인 요청에 따라 해설을 제공하며, 이번 응답에서는 이해도를 판정하지 않는다. |

- `analysis`의 판정은 충분·부족·모호 중 하나여야 한다. 코드용 판정 문자열은 별도로 합의한다.
- `explanation`의 판정은 반드시 `null`이다. 해설 제공을 충분·부족·모호로 분류하지 않는다.
- `null`은 설명을 분석했지만 의미가 불분명한 모호 판정과 다르다. 해설 응답에서 학습자의 이해도를 판정하지 않았음을 나타낸다.
- 해설 뒤 학습자가 재설명하면, 그 내용과 도움받은 맥락을 별도로 검토한다. 기존 초안은 `analysis` 평가를 제안했지만, 독립 회상이 미확인인 한국사 6번의 응답 종류·판정 조합은 미정이다. 앞서 해설을 제공했다는 사실만으로 충분이나 부족을 정하지 않는다.
- `explanation` 응답 자체는 충분 판정 개념 수에 포함하지 않는 방향을 제안한다. 실제 집계 처리와 저장 방법은 BE와 합의해야 한다.
- 나머지 분석 필드는 후속 논의에서 정한다. 이 절은 실행 가능한 스키마나 완성된 API 응답 예제가 아니다.

### 본문과 질문

| 필드 | 초안 타입 | 의미 |
| --- | --- | --- |
| `message` | 비어 있지 않은 문자열 | 이해 확인, 설명을 따라가다 막힌 상황, 요청받은 해설 등 사용자에게 보여줄 본문이다. |
| `question` | 비어 있지 않은 문자열 또는 `null` | 사용자에게 묻는 질문 하나다. 질문이 없으면 필드를 생략하지 않고 `null`을 넣는다. |

| 응답 종류와 판정 | `question` 규칙 |
| --- | --- |
| `analysis` + 충분 | `null`. 이해한 내용을 되짚고 질문 없이 마친다. |
| `analysis` + 부족 | 확인 질문 하나. 누락과 오류가 함께 있으면 오류를 우선한다. |
| `analysis` + 모호 | 불분명한 표현의 의미를 확인하는 질문 하나. |
| `explanation` + `null` | 해설을 바탕으로 자신의 말로 다시 설명해 달라는 질문 하나. |

- 질문은 `question`에만 담고 `message`에 중복하거나 추가 질문을 넣지 않는다. 질문 하나에 서로 다른 확인 과제를 묶지 않는다.
- 앱은 `message` 뒤에 `question`을 이어 보여줄 수 있다. 줄바꿈이나 말풍선 배치는 FE와 협의한다.
- 이 구조는 기존 질문 제한에 도달하기 전의 응답을 기준으로 한다. 질문 제한과 넘어가기 정책이 정해지면 종료 시점의 질문 유무도 별도로 합의한다.

3번 사례를 본문과 질문으로 나눈 부분 응답 예시:

```json
{
  "response_type": "analysis",
  "judgment": "부족",
  "message": "네 설명대로 가운데 값 4보다 큰 6을 찾으려고 왼쪽을 남겼는데, 6은 오른쪽에 있어서 놓쳤어.",
  "question": "내가 어느 부분을 잘못 따라간 거야?"
}
```

예시의 판정 문자열은 의미를 보여주기 위한 것이며 코드용 값은 아직 합의하지 않았다. `cases.json`의 `response_example`은 현재까지 합의한 전체 발화 예시로 유지하며, 이 작업에서 두 필드로 변환하지 않는다.

### 누락·오류와 확인된 개념

아래 세 필드는 내부 분석 기록이다. 캐릭터 말투는 적용하지 않고, 학습자의 실제 설명과 판단 근거에 따라 기록한다. 구조는 문서용 초안이며 필드 이름과 타입은 팀 검토 후 확정한다.

| 필드 | 초안 구조 | 의미 |
| --- | --- | --- |
| `omissions` | `{ concept, reason }` 목록 | 목표에 필요하지만 설명에서 빠진 내용과, 왜 그 내용이 필요한지를 기록한다. |
| `errors` | `{ statement, reason }` 목록 | 잘못된 설명과, 자료 또는 일반 지식에 비추어 왜 틀렸는지를 기록한다. |
| `confirmed_concepts` | `{ concept, evidence }` 목록 | 이번 설명에서 이해가 확인된 개념과, 학습자의 실제 설명에서 확인한 근거를 기록한다. |

- 각 항목의 값은 비어 있지 않은 문자열로 작성한다. 해당 항목이 없으면 필드를 생략하지 않고 빈 배열 `[]`을 사용한다.
- `omissions`는 설명에서 빠진 내용을 기록한다. 학습자가 그 내용을 모른다고 단정하는 근거로 사용하지 않는다.
- `errors.statement`는 실제 설명에서 확인할 수 있는 잘못된 명제를 기록한다. 말하지 않은 주장을 만들어 오류로 처리하지 않는다. `reason`은 판단 근거와의 충돌을 구체적으로 설명한다.
- `confirmed_concepts.evidence`는 학습자의 설명에서 확인한 내용을 인용하거나 충실하게 요약한다. AI가 제공한 해설을 학습자의 이해 근거로 사용하지 않는다.
- 전체 판정이 부족이어도 오류와 별개로 올바르게 설명한 부분은 `confirmed_concepts`에 남길 수 있다. 핵심 오류 때문에 성립하지 않는 연결이나 적용 능력까지 인정하지 않는다.
- 예를 들어 3번에서는 정렬 조건과 반복·종료 조건을 설명한 부분은 기록할 수 있지만, 올바른 탐색 방향이나 타겟을 보존하며 범위를 줄이는 원리를 이해했다고 인정하지 않는다.
- 모호한 내용은 질문으로 확인하기 전까지 누락·오류나 확인된 이해로 억지로 분류하지 않는다. 빈 배열은 이번에 확정해 기록한 항목이 없다는 뜻이며, 전체 이해가 충분하다는 뜻은 아니다.
- `explanation` 응답에서는 세 배열을 모두 비워 둔다. 해설 요청이나 AI의 설명 자체로 학습자의 누락·오류·이해를 새로 확정하지 않는다.
- 같은 개념을 여러 턴에서 설명했을 때의 중복 집계, 이후 오류가 수정됐을 때의 갱신 방식, 경험치 계산에 사용할 기준은 BE와 별도로 합의한다. 이 목록의 길이를 그대로 보상 수치로 사용하지 않는다.

3번 사례의 내부 분석 부분 예시:

```json
{
  "omissions": [],
  "errors": [
    {
      "statement": "오름차순이면 찾는 값이 중간값보다 클 때 왼쪽만 남기고, 작으면 오른쪽만 남긴다.",
      "reason": "참고 자료의 비교 방향과 반대다. 찾는 값이 중간값보다 크면 오른쪽을 남겨야 하는데, 설명대로 왼쪽을 남기면 타겟이 있는 범위를 제외한다."
    }
  ],
  "confirmed_concepts": [
    {
      "concept": "정렬 조건",
      "evidence": "학습자가 정렬된 배열에서 사용하는 방법이라고 설명했다."
    },
    {
      "concept": "반복과 종료 조건",
      "evidence": "남은 범위에서 반복하며, 같은 값을 찾거나 범위가 없어지면 종료한다고 설명했다."
    }
  ]
}
```

위 목록은 부분적으로 확인 가능한 내용을 보여주는 예시이며, 해당 사례의 모든 개념을 빠짐없이 나열한 정답 목록은 아니다. `cases.json`의 기존 평가용 문자열 목록은 이번 작업에서 바꾸지 않는다.

## AI 입력 계약 초안

이 절은 서버가 AI에 전달할 입력의 제안이다. 앱이 보내는 HTTP 요청 본문 전체를 뜻하지 않으며, 실제 `shared/` 스키마나 API를 변경한 것은 아니다. 어떤 정보를 서버에서 조회하고 조합할지는 BE와 협의한다.

| 필드 | 내용 |
| --- | --- |
| `learning_goal` | 이번 설명에서 확인할 학습 목표다. |
| `reference_materials` | 판단 근거로 사용할 참고 자료 내용의 목록이다. 자료가 없으면 빈 배열 `[]`을 전달한다. |
| `user_message` | 현재 사용자가 제출한 설명 또는 해설 요청이다. |
| `conversation_history` | 현재 메시지 이전까지의 동일 세션 대화 전체를 시간순으로 전달한다. 이전 대화가 없으면 빈 배열 `[]`이다. |
| `species_id` | 세션이 속한 폴더의 동물 ID다. `rubber_duck`, `raccoon`, `cat` 중 하나로 말투를 선택한다. |

### 참고 자료 항목의 상세 구조

`reference_materials`의 각 항목은 아래 형태를 제안한다. 필드와 타입은 문서용 초안이며 실제 공통 스키마는 팀 검토 후 확정한다.

| 필드 | 초안 타입 | 의미 |
| --- | --- | --- |
| `material_id` | 자료 고유 ID 문자열 | 어떤 자료를 판단 근거로 전달했는지 추적한다. |
| `title` | 비어 있지 않은 문자열 | 자료를 구분하는 제목이다. |
| `content` | 비어 있지 않은 문자열 | 자료에서 추출해 AI가 실제로 읽을 텍스트다. |

형태 예시의 ID는 설명용 자리표시자다. 실제 호출에서는 저장된 자료의 ID를 사용한다.

```json
{
  "material_id": "자료의 고유 ID",
  "title": "자료 제목",
  "content": "자료에서 추출한 텍스트"
}
```

- 자료가 없으면 `reference_materials`는 빈 배열 `[]`이다.
- 파일 경로나 자료 ID만 전달했다고 AI가 내용을 읽은 것으로 취급하지 않는다. 판단 근거로 사용할 실제 텍스트를 `content`에 전달한다.
- 이 항목 구조는 텍스트 전달 형태를 다룬다. 자료 선택 범위와 읽기 실패 원칙은 아래에 별도로 기록한다. 파일에서 텍스트를 추출하는 코드, 실패 상태 전달 방식과 긴 자료의 실제 처리는 아직 구현하지 않았다.

### 참고 자료 선택 범위와 변경 가능성

- 초기 MVP의 자료 선택은 A안으로 임시 채택한다. 현재 세션이 속한 과목 폴더의 전체 자료를 대상으로 하며 다른 과목 폴더의 자료는 포함하지 않는다.
- A안은 자료 선택 범위에 대한 AI 담당의 결정이다. 실제 조회·추출·전달 구현은 아직 없으며 FE·BE와 검토해야 한다.
- 자료가 많아 입력 한도를 넘는 경우의 처리는 미정이다. 읽기 실패 원칙은 다음 절에 기록하며, A안을 정했다는 이유로 모든 파일을 이미 읽었다고 취급하지 않는다.
- 향후 B안인 "사용자가 이번 학습에 사용할 자료를 선택"으로 변경할 가능성을 열어 둔다. B는 후속 대안이며 현재 MVP의 필수 선택 UI로 확정한 것은 아니다.
- B로 전환할 때는 FE의 선택 UI와 BE의 선택 자료 조회·검증을 함께 검토한다. 구체적인 선택 정보의 저장 및 API 형식은 그때 별도 합의한다.
- AI는 전달받은 `reference_materials` 목록을 판단 근거로 사용하도록 설계한다. 폴더 전체 선택과 사용자 선택은 목록을 조합하는 단계에서 구분해, AI 분석 형식에 A만을 전제로 고정하지 않는 방향을 제안한다.

### 자료를 읽지 못했을 때의 처리 원칙

이 절은 AI 담당자가 승인한 동작 원칙이며, FE·BE의 실제 화면과 처리 코드는 아직 구현하지 않았다.

- 일부 자료만 읽혔으면 실제로 읽은 자료를 근거로 대화를 계속한다. 사용한 자료와 읽지 못한 자료를 구분해 사용자에게 안내한다.
- 읽지 못한 자료의 내용을 추측하거나, 폴더의 자료 전체를 검토했다고 말하지 않는다.
- 읽지 못한 자료에 관련 내용이 있을 수 있으므로, 일부만 읽은 상태에서 폴더의 모든 자료에 해당 내용이 없다고 단정하지 않는다. 판단 범위는 실제 전달받은 자료로 한정한다.
- 자료가 있지만 하나도 읽지 못했으면 일반 지식으로 계속할지 사용자에게 확인한다. 자료가 처음부터 없는 경우와 구분하며, 동의 없이 일반 지식으로 자동 전환하지 않는다.
- 사용자가 일반 지식으로 계속하기를 선택하면 기존의 일반 지식 기반 대화·정확성 안내 원칙을 적용한다. 사용자의 선택 전에는 동의한 것으로 취급하지 않는다.
- 사용·실패 자료의 안내 방식과 계속 여부 확인 UI, 추출 결과를 AI와 앱에 전달하는 필드 및 상태는 FE·BE와 별도로 합의한다. `reference_materials: []`만으로 원래 자료가 없었던 경우와 전체 읽기 실패를 구분할 수 있다고 가정하지 않는다.
- 읽기 실패를 알리는 원칙만 정한 것이며, 파일 재시도·재업로드 흐름이나 입력 한도 초과 처리는 아직 정하지 않았다.

### 이전 대화 항목의 상세 구조

`conversation_history`의 각 항목은 발화자와 실제 발화 내용으로 구성한다. 필드와 타입은 공통 계약 검토를 위한 초안이다.

| 필드 | 초안 타입 | 의미 |
| --- | --- | --- |
| `role` | `user` 또는 `assistant` | 사용자 발화와 AI 발화를 구분한다. |
| `content` | 비어 있지 않은 문자열 | 해당 발화의 실제 내용이다. |

```json
[
  {
    "role": "user",
    "content": "이진 탐색은 정렬된 배열에서 쓰는 방법이야."
  },
  {
    "role": "assistant",
    "content": "정렬되어 있어야 하는 거구나. 그 조건이 범위를 줄이는 데 어떻게 도움이 되는 거야?"
  }
]
```

- AI 응답은 `message` 뒤에 `question`을 순서대로 이어 하나의 `content`로 보존한다. `question`이 `null`이면 본문만 넣으며, 문자열 `null`을 덧붙이지 않는다.
- 내부 판정, 누락·오류 기록, 확인된 개념 및 분석 근거는 대화 내용에 섞지 않는다. 이 항목은 사용자와 AI 사이의 실제 발화를 전달하기 위한 것이다.

### 이전 대화 전달 규칙

- 현재 세션의 사용자·AI 발화를 모두 포함한다. 최근 몇 턴만 선택하는 방식은 초기 MVP의 기본안으로 사용하지 않는다.
- 각 발화에는 위의 `role`과 `content`를 기록하고 실제 발화 순서를 유지한다.
- AI가 앞서 한 질문, 이해 확인, 제공한 해설도 보존해 같은 질문의 반복이나 대화 맥락의 누락을 줄인다.
- 현재 메시지는 `user_message`에 한 번만 넣고 `conversation_history`에는 중복해서 넣지 않는다.
- 다른 학습 세션의 대화는 포함하지 않는다.
- AI의 해설과 사용자의 설명을 구분한다. AI가 말한 내용을 학습자가 이해했다는 근거로 사용하지 않는다.
- 입력 한도를 넘을 때의 처리는 모델 선정 후 별도로 정한다. 초안 단계에서 과거 대화를 임의로 잘라내는 규칙을 추가하지 않는다. 전체 대화 전달이 모델의 입력 한도를 없애는 것은 아니므로 실제 연결 전에 한도 초과 처리 방식을 마련해야 한다.

자료 선택 범위는 A안으로 임시 채택했으며 B 전환 가능성과 읽기 실패 원칙도 기록했다. 실제 조회·추출 방식, 실패 상태 전달과 확인 UI, 입력 한도 초과 처리는 아직 정하지 않았다. 기존 `cases.json`의 평가용 입력은 이번 작업에서 이 계약 초안으로 변환하지 않는다.

## 기존 설계와의 연결

- 캐릭터별 표현을 적용해도 분석과 판정 기준은 동일하게 유지한다.
- 이 문서의 충분 응답은 다음 주제를 자동 제안하지 않는 방향이다. 기존 `CLAUDE.md`의 충분 이후 다음 주제 제안 흐름과 차이가 있으므로, FE·BE와 연결하기 전에 팀에 공유하고 공통 문서 및 계약에 반영할지 합의한다.
- 공통 데이터 타입과 스키마는 `shared/`에서 별도 PR로 합의한다. 이 문서는 필드 이름이나 스키마를 확정하지 않는다.
- 일반 지식 기반의 정확성 안내를 발화 밖에서 제공하는 방식은 FE와 협의해 연결한다. 안내 문구를 AI 발화에서 뺐다는 것이 실제 화면에 안내를 구현했다는 뜻은 아니다.
- 해설 요청 턴은 위 출력 계약 초안처럼 응답 종류와 판정을 분리하는 방향을 제안한다. API·DB의 실제 스키마와 집계 처리는 FE·BE와 합의한 뒤 별도로 구현하며, 평가 자료를 그대로 서버 스키마로 사용하지 않는다.

## 미정 사항과 후속 검토

- A안의 실제 자료 조회·추출·입력 조합과 모델 입력 한도 초과 처리
- 읽기 실패 상태 전달 필드, 사용·실패 자료 안내 및 일반 지식 전환 확인 UI
- B안 전환 시 선택 UI·API·저장 방식 (향후 변경 후보)
- 분석 출력의 필드 이름, 타입, 필수 항목과 판정별 조합
- 계산 오류와 개념 이해의 분리, 확인 전 유보·도움받은 회상·질문 없는 종료의 계약 표현
- 현재 세션의 기술별 이전 수행 근거 참조·갱신과 보상·리포트 반영
- 추가 14개 사례의 평가 입력·출력 형식 변환, 실제 이전 대화 구성 및 한국사 원문 재사용 범위
- 정확성 안내 UI의 구체적인 배치와 표시 동작 (FE 협의)
- 자료 내부의 충돌, 자료만으로 판단하기 어려운 내용, 모델의 지식이 불확실한 경우의 처리
- 질문 최대 반복 횟수와 넘어가기 동작
- 해설 요청 턴과 판정 보류를 공통 계약 및 집계에서 표현하는 방법
- 캐릭터별 최종 말투, OpenAI API의 운영 조건 검토·모델 선정과 STT 제공자
- 평가 실행 방법과 후속 대화를 포함한 추가 사례
