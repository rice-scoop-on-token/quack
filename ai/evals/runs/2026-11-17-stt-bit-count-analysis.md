# 음성 전사에서 비트 수가 불명확할 때 설명 분석 비교

2026-11-17 한국 시간 기준, [STT PR #26](https://github.com/rice-scoop-on-token/quack/pull/26)의 `6c14146` 분석 코드로 평가했다. 비교 질문은 “학습 목표에 필요한 비트 수가 불명확한 경우 AI가 이해한 부분을 되짚고 해당 숫자만 다시 묻는가”다.

## 입력과 조건

- Chrome WebM/Opus 두 파일을 `gpt-transcribe`로 각각 한 번 전사했다. 한국어 힌트를 사용했고 용어 힌트와 재시도는 없었다. 실제 전사문에서 두 비트 수는 정확하게 인식됐다.
- 오류 재현 입력은 각 실제 전사문의 끝 표현만 바꿨다. 아래 재현문은 실제로 관측된 전사 오류가 아니다.
- 분석은 `gpt-6.1-sol`, 출력 한도 4,096토큰, 대기 한도 30초, `input_mode: "voice"`, 캐릭터 `rubber_duck`으로 실행했다. 참고 자료와 대화 이력은 비웠다. 조건별 한 번씩 총 4회 호출했다.

### RISC-V의 ADD·SUB 구분과 rd 필드

학습 목표는 RV32I에서 ADD와 SUB를 어떻게 구분하는지, 결과를 저장할 레지스터의 번호를 rd에 몇 비트로 담는지 설명하는 것이다.

- 파일은 `riscv-rd.webm`(17.76초, 287,198바이트)이다.
- 실제 전사문

  > add랑 sub는 opcode랑 func3가 같아서 func7으로 구분해. rs1이랑 rs2는 읽을 레지스터를 고르고, rd는 결과를 저장할 레지스터를 골라. rd의 레지스터 번호를 담는 데 5비트.

- 오류 재현에서는 마지막 `5비트.`를 `다… 비트.`로 바꿨다.
- 실제 전사문 응답

  > ADD와 SUB는 opcode와 funct3가 같아 funct7으로 구분하고, rd에는 결과를 저장할 레지스터 번호를 5비트로 담는 거구나.

- 오류 재현 응답

  > ADD와 SUB는 opcode와 funct3가 같아 funct7으로 구분한다는 거구나. rs1·rs2는 읽을 레지스터를, rd는 결과를 저장할 레지스터를 고른다는 설명도 따라갔어.

### 2의 보수 부호 확장의 추가 비트 수

학습 목표는 8비트 음수를 16비트로 부호 확장할 때 어느 쪽에 어떤 값을 몇 비트 추가하는지 설명하는 것이다.

- 파일은 `sign-extension.webm`(9.24초, 150,026바이트)이다. 대본의 “기존 비트”는 “기준 비트”로 전사됐다.
- 실제 전사문

  > 8비트 음수를 16비트로 부호 확장할 때 기준 비트는 그대로 둬. 맨 왼쪽 부호 비트가 1이니까 왼쪽을 1로 채워. 새로 붙이는 건 8비트.

- 오류 재현에서는 마지막 `8비트.`를 `여러 비트.`로 바꿨다.
- 실제 전사문 응답

  > 음수의 부호 비트가 1이라서, 왼쪽에 1을 8개 붙여 16비트로 만드는 거구나.

- 오류 재현 응답

  > 부호 비트가 1이라서 왼쪽에 1을 붙인다는 건 이해했어.
  >
  > 8비트를 16비트로 만들려면 왼쪽에 1을 몇 비트 붙이는 거야?

## 변경 전 결과

| 사례와 조건 | 답 상태 | 이해 | 독립 수행 | 행동 | 오류 / 누락 | 행동 기준 |
| --- | --- | --- | --- | --- | --- | --- |
| RISC-V · 실제 전사 | `not_applicable` | `sufficient` | `confirmed` | `acknowledge` | 0 / 0 | 충족 |
| RISC-V · 숫자 불명확 | `unverified` | `unverified` | `unverified` | `acknowledge` | 0 / 0 | 필요한 질문을 하지 않음 |
| 부호 확장 · 실제 전사 | `not_applicable` | `sufficient` | `confirmed` | `acknowledge` | 0 / 0 | 충족 |
| 부호 확장 · 숫자 불명확 | `unverified` | `unverified` | `unverified` | `ask` | 0 / 1 | 질문은 적절했고 비트 수를 누락으로 기록함 |

두 오류 재현 응답은 또렷하게 전달된 관계를 인정했고 정확한 숫자를 대신 말하지 않았다. RISC-V 응답은 rd의 비트 수를 끝내 묻지 않았다. 부호 확장 응답은 해당 숫자를 물었지만, `omissions`에 “새로 붙이는 비트를 '여러 비트'라고만 설명했다”고 기록했다. “여러 비트”는 실제 서비스에서는 학습자 본인의 모호한 표현일 수도 있다. 이번 비교에서는 숫자만 치환했으므로, 모델이 전사 오류의 원인을 자체적으로 식별할 수 있다는 근거로 사용하지 않는다.

전사 2회는 HTTP 200이었다. 제공자 기준 총 28초로 추정 비용은 $0.0021이다. 분석 4회는 모두 HTTP 200과 내부 출력 검증을 통과했고 재시도는 없었다. 입력 11,537토큰 중 캐시 읽기 8,265토큰, 캐시 쓰기 3,260토큰, 기타 12토큰이다. 출력은 1,764토큰이고 추정 비용은 $0.02664다. [전사 단가](https://developers.openai.com/api/docs/models/gpt-transcribe), [분석 모델 단가](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

## 변경 후 재평가

변경 전과 같은 네 입력을 같은 모델과 설정으로 한 번씩 다시 분석했다. 숫자가 불명확한 두 입력에서는 명확히 전달된 개념을 되짚고 필요한 비트 수만 질문하는지, 해당 숫자에 의존하는 판정을 보류하는지, 오류와 누락에 넣지 않는지를 확인했다. 숫자가 정확한 두 입력은 이해를 충분으로 판정하고 질문 없이 인정하는지 확인했다.

| 사례와 조건 | 답 상태 | 이해 | 독립 수행 | 행동 | 오류 / 누락 |
| --- | --- | --- | --- | --- | --- |
| RISC-V · 실제 전사 | `correct` | `sufficient` | `confirmed` | `acknowledge` | 0 / 0 |
| RISC-V · 숫자 불명확 | `unverified` | `unverified` | `unverified` | `ask` | 0 / 0 |
| 부호 확장 · 실제 전사 | `not_applicable` | `sufficient` | `confirmed` | `acknowledge` | 0 / 0 |
| 부호 확장 · 숫자 불명확 | `unverified` | `unverified` | `unverified` | `ask` | 0 / 0 |

**RISC-V · 실제 전사**

> ADD와 SUB는 opcode와 funct3가 같아서 funct7으로 구분하는 거구나. rs1·rs2는 읽을 레지스터를, 5비트인 rd는 결과를 저장할 레지스터를 지정하고.

**RISC-V · 숫자 불명확**

> ADD와 SUB는 funct7으로 구분하고, rd는 결과를 저장할 레지스터를 고른다는 설명은 이해했어.
>
> rd에 레지스터 번호를 담는 데 몇 비트가 필요하다고 말한 거야?

**부호 확장 · 실제 전사**

> 음수의 부호 비트가 1이니까, 기존 8비트는 그대로 두고 왼쪽에 1을 8개 붙여 16비트로 만드는 거구나.

**부호 확장 · 숫자 불명확**

> 부호 비트가 1이라 왼쪽을 1로 채운다는 건 이해했어.
>
> 이때 새로 붙이는 1은 몇 비트야?

네 입력 모두 위 행동 기준을 충족했다. RISC-V 오류 재현은 `acknowledge`에서 `ask`로 바뀌었고, 부호 확장 오류 재현은 필요한 질문을 이어가면서 누락 기록이 1건에서 0건으로 줄었다. 정확한 전사문 두 건은 `sufficient`·`acknowledge`를 유지했다. RISC-V 실제 전사문의 답 상태는 `not_applicable`에서 `correct`로 바뀌었다. 조건마다 한 번만 호출했으므로 어떤 변화가 프롬프트에 따른 것인지, 반복해도 같은 결과가 나오는지는 이 비교만으로 확인할 수 없다.

네 분석 모두 HTTP 200과 내부 출력 검증을 통과했고 재시도는 없었다. 입력 12,041토큰 중 캐시 읽기 8,643토큰, 캐시 쓰기 3,386토큰, 기타 12토큰이다. 출력은 1,583토큰이고 추정 비용은 $0.02518다. [분석 모델 단가](https://developers.openai.com/api/docs/models/gpt-6.1-sol).
